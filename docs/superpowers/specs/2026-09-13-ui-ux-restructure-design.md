## 0. 배경 — 무엇이 문제였나

사용자 평가는 "색이 아니라 쓰면서 불편한 것들"이었다. 실제 코드와 화면 캡처
(`build/manual_shots/*.png`)를 대조해 확인한 것은 아래 일곱 가지다. 시각 토큰
(`ui/theme.py`)은 대비도 단일 진실도 지켜지고 있어 **색은 그대로 둔다**.

**A. 주 동작에 고정된 자리가 없다.** 탐색은 캔버스 위 툴바 `[그리기]`, 요약은
두 번째 왼쪽 칼럼 `[표 만들기]`, 리포트는 본문 상단 `[미리보기]`, `[적용]`은
왼쪽 도크 한가운데. 탭을 옮길 때마다 누를 것을 눈으로 찾아야 한다.

**B. 한 개념이 두세 군데로 쪼개져 있다.** 그룹은 *보이기*=도크 리스트,
*스타일*=탐색 인스펙터와 리포트 인스펙터에 각각 한 벌, *편집*=도크 버튼 →
다이얼로그. 리포트 화면 한 장면에 `[모든 plot에 적용]`이 두 개 있고 뜻이 다르다
(`report.py:223`은 점 표시, `style_card`는 그룹 스타일).

**C. 왼쪽 도크가 10개 섹션짜리 스크롤 벽이다.** 설정·파일·LOT·적용·힌트 2블록·
표시·그룹·이상치 필터·제외·도구. 섹션 머리 관용구가 두 종류 섞여 있고
(`SectionLabel` 대문자 vs `CollapsibleSection ▸`), 도크 스크롤 **안에** lot
리스트(132px)와 그룹 리스트(120px)가 각자 또 스크롤한다. 이상치·제외·도구는
접힌 데다 스크롤 아래라 사실상 미발견 기능이다.

**D. "즉시 반영"과 "[적용] 필요"가 한 칼럼에 섞여 있다.** 로그 패턴(즉시)·
lot 심볼(즉시) 바로 위에 lot 선택([적용])·파일([적용])이 구분 없이 놓인다.
사용자가 규칙을 배울 방법이 없다.

**E. 칼럼이 넷이다.** 리포트 화면은 도크 300 + 페이지 목록 158 + 캔버스 +
인스펙터 292. 1366×768에서 캔버스가 616px만 남아 plot 6장이 엄지손톱이 된다.

**F. 데이터 화면에 빈 카드가 있다.** 기간 카드의 위 2/3가 통째로 비고 좌우 칼럼
높이가 맞지 않는다.

**G. 첫 실행 안내가 없다.** 아무것도 안 물린 상태의 캔버스는 빈 회색이고, 파일
5행이 전부 똑같이 "고르기"라 무엇이 필수인지 알 수 없다.

여기에 사용자가 추가로 요청한 둘을 합친다: **성능·OOM 개선**(SQL·추출·plot
핸들링)과 **입력 가이드**(채워야 할 칸을 시각적으로 알리기).

### 확정된 전제

- 주 사용 루프는 셋이다: **추출 → 적재 → PPT**, **요약표 뽑아 공유**,
  **실험(split) 그룹 비교**. 탐색(그려보며 이상점 찾기)은 주 루프가 아니다 —
  지금 탐색이 전용 인스펙터까지 갖고 가장 넓은 자리를 쓰는 비중을 뒤집는다.
- 현장 PC에 **1366×768 노트북이 섞여 있다.** 모든 레이아웃은 이 크기에서
  깨지지 않아야 한다.
- 기능은 하나도 빼지 않는다. 자리와 흐름만 바꾼다.

## 1. 지배 규칙

도크가 지저분한 근본 원인은 폭도 색도 아니라 **"이 칼럼에 무엇이 들어가야
하는가"에 대한 규칙이 없다**는 것이다. 규칙부터 세우고 나머지를 거기에 맞춘다.

### 규칙 1 — 왼쪽은 "무엇을 보고 있나", 오른쪽은 "그것을 어떻게 보일까"

**왼쪽 레일 = 분석 데이터셋을 정하는 것.** 어떤 DB·템플릿·리포메터를 쓰는지,
어느 lot을 읽는지, 어떤 점을 버리는지(이상치 필터), 어떤 컬럼을 덧붙이는지
(inline 계측·fab tracking). 이것들을 바꾸면 **볼 수 있는 것 자체가 달라진다.**

**오른쪽 인스펙터 = 이미 정해진 데이터셋의 표현.** 축·스케일·그룹 색·표 집계·
슬롯 배치. 이것들은 데이터를 바꾸지 않는다.

여기서 D(즉시 반영과 [적용] 필요가 섞여 있음)가 자동으로 풀린다. 왼쪽은 대부분
`[적용]`이 필요하고 오른쪽은 전부 즉시이거나 `[그리기]`다. 다만 **[적용] 필요
여부가 규칙이 아니라 결과**라는 점이 중요하다 — 계측·tracking은 `[적용]` 없이
즉시 붙지만 데이터셋을 바꾸므로 왼쪽이다. `[적용]`이 필요한 왼쪽 항목은
`[적용]` 버튼이 dirty가 되어 스스로 알린다(기존 규약 그대로).

새 컨트롤을 넣을 때 물을 것: **"이게 데이터를 바꾸나, 표현을 바꾸나."**

### 규칙 2 — 한 개념은 한 곳

그룹은 인스펙터 `[그룹]` 섹션 하나가 *보이기 · 색/심볼/크기 · REF · 편집*을
전부 갖는다. 같은 개념의 컨트롤을 두 화면에 복제하지 않는다.

### 규칙 3 — 주 동작은 움직이지 않는다

하단 액션바 **왼쪽 끝**이 영구 주소다. 탭이 바뀌면 라벨만 바뀐다
(`그리기` / `표 만들기` / `미리보기`). 오른쪽 끝은 **결과를 꺼내는 자리**이고,
주 사용 루프 두 개(요약표 공유·PPT)가 여기서 항상 한 번에 닿는다.

### 규칙 4 — 필수 입력은 화면이 먼저 말한다

비어 있는 필수 입력은 사용자가 묻기 전에 표시된다(§6). 무엇이 필수인지는
`ui/guidance.py` 한 곳이 판정한다.

### 1366×768 계산 (설계 근거)

**가로** 244 + 272 = 516 → 캔버스 **850px**. 현재 리포트 탭은 300+158+292=750을
먹어 캔버스가 616px뿐이다. 양쪽 패널은 각각 접힌다(`F9` 소스 / `F10` 인스펙터).
둘 다 접으면 약 1350px.

**세로** 46+36+42 = 124 → 본문 644px. 새 왼쪽 레일은 프리셋 34 + 파일 5×40 +
접힘 섹션 3×30 + 구분 + `[적용]` 60 + 상태 요약 50 ≈ **440px**.
**스크롤이 사라진다** — C의 해소가 여기서 일어난다.

### 이동표 (무엇을 어디로)

| 지금 | 어디로 | 근거 |
|---|---|---|
| 도크 `저장/새이름/삭제` 3버튼 | 프리셋 콤보 옆 `⋯` 메뉴 | 드물게 쓰는 동작이 primary 색과 최상단을 먹고 있다 |
| 도크 `표시`(로그 패턴·lot 심볼) | 인스펙터 `[보기]` | 표현만 바꾸고 데이터를 바꾸지 않는다 → 규칙 1 |

| 도크 `도구` → `inline 계측`·`fab tracking` | 왼쪽 레일 `추가 소스` 절 | 분석 프레임에 컬럼을 붙여 **그릴 수 있는 것이 달라진다** → 규칙 1 |

| 도크 힌트 2블록(4줄 산문) | 상태 레일 · `[적용]` 툴팁 | 조작면에 산문이 상주할 이유가 없다 |
| 요약 `도구` 스트립(2번째 칼럼) | 액션바 + 인스펙터 `[표]` | 칼럼 하나 제거 |
| 리포트 `페이지 목록`(세로 158px) | 슬라이드 위 **가로 페이지 스트립** | 158px를 캔버스에 반환 |
| 리포트 `표 슬라이드` 설정 | 인스펙터 `[덱]` | 슬롯 설정이 아니라 덱 설정이다 |
| `[모든 plot에 적용]` ×2 | `[점 표시를 전 슬롯에]` / `[스타일을 전 plot에]` | 같은 라벨 두 개는 버그 |

### 페이지 스트립 (페이지 수가 3장일 수도 30장일 수도 있음)

브라우저 탭 방식으로 만든다: 칩 나열 + 넘치면 가로 스크롤 + `◀ ▶` + `⌄`로 전체
목록 팝업. 3장이면 전부 보이고 30장이어도 깨지지 않는다. 세로 36px만 쓴다.

### 고정 폭 상수

`analysis_ws.DOCK_WIDTH = 300`은 `source_rail.RAIL_WIDTH = 244`로,
인스펙터는 `INSPECTOR_WIDTH = 272`로 옮긴다. CLAUDE.md가 적어 둔 계약
("도크에 넣는 위젯은 고정 폭 안에 들어가야 한다 — 가로 스크롤이 없어 넘긴
위젯은 오류 없이 오른쪽이 잘린 채로 남는다")은 **두 패널 모두에 그대로
적용**되고, 콤보의 `sizeAdjustPolicy`를 자리 기준으로 바꾸는 처리도 두 곳에서
유지한다.

### 데이터 화면

같은 액션바 관용구를 쓴다(하단 고정: `[추출하고 적재]` · 중지 · 옵션 · 예약).
기간 카드의 빈 2/3는 **기간을 조회 조건 카드 안으로 넣어** 해소한다. 좌우 칼럼
높이를 맞춘다.

## 3. 인스펙터와 탭

### 인스펙터는 워크스페이스가 하나만 소유한다

탭이 바뀌면 **전용 섹션만 갈아 끼우고**, `그룹`·`보기` 두 섹션은 진짜 단일
인스턴스로 남는다. 규칙 2를 화면뿐 아니라 코드에서도 지키기 위한 구조다.

```
탐색    : 축 → 스케일·범위 → [그룹] → [보기]
요약    : 표            → [그룹] → [보기]
리포트  : 슬롯 → 덱      → [그룹] → [보기]
```

### `[그룹]` 섹션 — 흩어진 넷을 하나로

```
── 그룹                                    3개
 ☑ ◆ Base                     REF     458
 ☑ ● Split_A                          412
 ☑ ■ Split_B                          420
 ─────────────────────────────────────────
 [색] [◆ 마름모 ⌄] [6 ⌄]   ← 위에서 고른 행에 적용
 ☐ 이 그룹을 REF로
 [스타일을 전 plot에]       [그룹 편집…]
 ⚠ 혼입 6건 — 'Base' 안에 M5 2종
```

리스트에서 고른 행이 곧 편집 대상이므로 **지금의 `그룹 고르기` 콤보가 통째로
사라진다** — 도크 리스트와 인스펙터 콤보가 같은 일을 두 번 하고 있었다.

### `[보기]` 섹션

로그 축 item 패턴 · `lot마다 심볼 다르게` · `범위 직접 지정`(탐색에서만 X/Y
입력 노출). 전부 즉시 반영 항목이다.

### 탭별 정리

- **탐색** — 캔버스 위 툴바에서 `[그리기]`·`[＋리포트에 추가]`를 액션바로 보내고
  `클릭 → 제외/복원` 토글만 캔버스 좌상단에 남긴다.
- **요약** — 2번째 칼럼 삭제. 표마다 똑같이 반복되던 캡션
  (`M2_ET · 그룹별 평균 · 제외 2점 반영 · 붉은 셀은…`)은 표 영역 상단 한 줄로
  합친다. 카드별 `복사`·`xlsx`는 유용하므로 유지.
- **리포트** — 슬라이드가 남는 폭을 전부 써서 썸네일이 약 1.4배가 된다.

### 빈 상태

세 탭 모두 본문 가운데에 "지금 무엇이 없고 → 무엇을 누르면 되는지"를 그린다.
문구는 §6의 `guidance` 단일 진실에서 가져온다(빈 상태와 가이드가 다른 말을 하면
안 된다). 파일 5행은 `●필수 / ○선택`으로 갈라 표시한다.

## 4. 성능과 OOM

### 4-A. 추출 OOM (`data/extractor.py`)

```python
def _fetch(sql):                 # extractor.py:95
    pdf = bdq.getData(sql)       # pandas 전체가 메모리로
    return pl.from_pandas(pdf)   # polars 복사본 — 둘이 동시에 살아 있다
```

`N_WORKERS = 4`이므로 **피크가 프레임 8벌**이다(워커당 pandas 1 + polars 1).
여기에 셋이 겹친다.

1. **`MemoryError`를 재시도한다.** `extractor.py:224`의 `except Exception`이
   `MemoryError`를 잡아 `RETRY=2`로 두 번 더 시도한다. 이미 메모리가 터진
   상태에서 같은 쿼리를 두 번 더 던지므로 반드시 더 나빠진다.
2. **한 청크가 터져도 나머지 3워커가 계속 돈다.** `ThreadPoolExecutor`는 제출된
   future를 취소하지 않는다.
3. **청크 상한이 행 수·바이트 기준이 아니다.** 상한은 기간(1일)과 item 9999개
   뿐인데 9999는 Impala `IN` 상한이지 메모리와 무관하다. item이 1000개면 그룹이
   1개라 **하루치가 통째로 한 청크**다.

| 조치 | 내용 |
|---|---|
| pandas 즉시 해제 | `pl.from_pandas` 직후 `del pdf`. 먼저 `pa.Table.from_pandas` → `pl.from_arrow` 무복사 경로를 시도하고 실패 시 현행 폴백 |
| OOM 재시도 금지 | `MemoryError`·`pyarrow.ArrowMemoryError`는 `RETRY` 루프에서 즉시 탈출. 재시도는 네트워크·일시 오류에만 |
| 실패 시 즉시 중단 | 첫 예외에서 내부 stop 플래그를 세워 남은 unit이 조회를 시작하지 않게 한다(`should_stop`과 같은 통로) |
| 메모리 예산 기반 워커 | `N_WORKERS` 고정 → `plan_workers(가용 메모리, 첫 청크 `estimated_size()`)`. 상한 4 하한 1, 설정으로도 노출 |
| 행 수 기준 분할 | `plan_units`에 `max_rows` 추가. 첫 청크 실측이 예산을 넘으면 item 그룹을 더 잘게 쪼갠다(기간은 1일이 이미 최소) |
| 사용자에게 말한다 | OOM을 잡아 "기간을 줄이거나 item 조건을 좁히세요 · 동시 실행 N→N−1"로 안내 |

### 4-B. SQL 창 (`ui/widgets/sql_dialog.py`)

미리보기 `LIMIT 200` + 저장 `COPY TO` 스트리밍은 **이미 잘 돼 있다.** 남은
구멍만 막는다.

- **SBDF 경로**(`sql_dialog.py:257`)가 `.pl()` 전체 + `.to_pandas()`로 2벌을
  올린다. 경고만 하고 막지 않는다 → parquet으로 흘린 뒤 변환, sbdf가 pandas만
  받으면 최소한 즉시 해제 + 상한 초과 시 차단.
- **`preview_query`가 쿼리를 두 번 실행한다**(`LIMIT 200` 1회 + `count(*)` 1회).
  무거운 집계면 시간이 2배 → 전체 행 수는 지연 계산으로 옮긴다.
- **DuckDB `readonly_config()`에 `memory_limit`이 없다**(`loader.py:28-48`).
  `temp_directory`는 **이미 설정돼 있다**(디스크 스필용, `{"threads": 4}`만
  돌려주는 것은 mkdir이 실패했을 때의 폴백 경로다). 빠진 것은 상한뿐이라,
  DuckDB가 기본값인 **물리 메모리의 80%**까지 쓴다. 현장 PC는 Excel COM과
  메모리를 나눠 쓰므로 이 기본값이 과하다 → 명시적 `memory_limit`으로 예측
  가능한 천장을 준다. 단, 과거 로그의 `Arrow buffer failed to allocate`는
  DuckDB 내부가 아니라 **결과를 파이썬으로 실체화하는 쪽**에서 났으므로
  `memory_limit`이 그 사고를 직접 막지는 않는다 — 그쪽은 이미 `LIMIT 200` +
  `COPY TO`로 막혀 있고, 여기서 얻는 것은 DuckDB가 다른 프로세스를 굶기지
  않게 하는 것이다.

### 4-C. Plot 핸들링 (지목된 UI 병목)

확인된 것 다섯:

1. **`_collect_points()`가 클릭 제외가 꺼져 있어도 항상 돈다.**
   `plot_canvas.py:93`이 `on_pick` 여부와 무관하게 호출한다. 리포트 탭은 캔버스가
   6개라 미리보기 한 번에 `key.to_list()`가 6번 — 20만 행이면 파이썬 문자열 객체
   120만 개가 만들어졌다 버려진다. **`if self.on_pick is None: return` 한 줄이
   가장 큰 즉효다.**
2. **그룹 분할이 그룹 수만큼 전체 스캔이다**(`plot_canvas.py:59`,
   `{gid: active.filter(gid == g.gid)}`). `partition_by("gid")` 1회로
   O(n×g) → O(n).
3. **`active()`·`hidden()`에 캐시가 없다**(`state.py:99`). 슬롯 6개가
   `is_in(list(hidden))`을 6번, `_excluded_frame()`이 또 6번 돈다.
   `data`·`hidden` 버전 카운터로 무효화하는 캐시를 `AppState`에 둔다.
4. **`ax.scatter`(PathCollection)를 쓰는데 그룹 안에서 색·크기가 균일하다**
   (`mpl_renderer.py:159`). 균일할 때는 `ax.plot(..., linestyle="none",
   marker=...)`(Line2D)가 같은 그림을 5~10배 빠르게 그린다. 점을 하나도 버리지
   않으므로 "이상점 찾기"의 정직성이 유지된다 — **샘플링·decimation은 쓰지
   않는다.**
5. 클릭 히트테스트가 전체 점을 순방향 픽셀 변환한다(`plot_canvas.py:149`) →
   클릭 좌표를 **역변환 1회**로 데이터 공간에 옮겨 비교한다.

1·2·3·4는 리포트 탭에서 전부 6배로 걸리는 자리라 미리보기가 가장 크게 줄고,
탐색 탭 `[그리기]`는 4번이 주로 듣는다. 단계 7에서 `pytest -m slow -s`의 단계별
시간으로 전후를 숫자로 남긴다.

### 건드리지 않는 것

matplotlib 렌더는 UI 스레드 유지(워커로 옮기면 폰트·텍스트 메트릭 캐시가 스레드

## 5. 입력 가이드

"지금 내가 채워야 하는 칸이 어디인가"를 화면이 직접 말하게 한다. 두 층.

**층 1 — 필요 표시 (상시·수동적).** 비어 있는데 꼭 필요한 입력은 위젯 속성
`needs="true"`를 달고 QSS가 왼쪽에 액센트 바 + 테두리를 그린다. 채우면 조용히
사라진다. 규칙이 QSS 한 줄이라 **모든 창에 자동으로 적용된다** — 왼쪽 레일 파일
행, 데이터 화면 `line_id`, 계측·tracking 창의 필수 조건, 리포트 슬롯의 X·Y까지.

**층 2 — 가이드 모드 (요청 시·능동적).** 상단바 `?` 또는 `F2`로 켜면 그 화면에서
**다음에 할 한 곳만** 강조하고 한 줄 설명을 붙인다. 다 채우면 자동으로 꺼진다.

```
분석  : ① DB → ② Plot/Table 템플릿 → ③ 리포메터 → ④ [적용] → ⑤ 그룹
데이터: ① 대상 DB → ② 리포메터 → ③ line_id → ④ 기간 → ⑤ [추출하고 적재]
```

### 설계 원칙

- **오버레이를 쓰지 않는다.** 떠 있는 말풍선은 스크롤·리사이즈·패널 접기에서
  어긋난다. 강조는 위젯 자신의 속성으로 그린다.
- **색만으로 알리지 않는다.** 테두리 + 라벨의 `*` + 툴팁을 함께 단다(이
  프로젝트가 dirty 표시에서 이미 쓰는 규칙).
- **무엇이 필수인지는 한 곳에서만 판정한다.** `ui/guidance.py`의
  `analysis_requirements(state, cfg)` / `data_requirements(preset)`가 순서 있는
  `Requirement` 목록을 돌려주고, **빈 상태 화면·필요 표시·가이드 모드 셋이 같은
  함수를 읽는다.** `[적용]`의 실제 검증과 어긋나면 "표시는 초록인데 적용은 실패"가
  되므로 여기가 단일 진실이다.

## 8. 리스크

- **인스펙터를 워크스페이스 소유로 바꾸면** 탭이 자기 위젯을 직접 참조하던 코드
  (테스트 포함)가 끊긴다 → 각 탭에 `inspector_sections()`만 두고 기존 속성
  이름(`cmb_group`·`chk_ref`·`btn_color` 등)은 property로 남겨 완충한다.
- **matplotlib 렌더를 워커로 옮기고 싶어지는 유혹** — 옮기면 프로세스가 죽는다.
  단계 4에서 성능을 손볼 때 이 경계를 넘지 않는다.
- **설명서 PDF는 화면이 바뀌면 무효다.** 단계 7에서 `tools/make_manual.py`를
  반드시 다시 돌린다.
- **`Line2D` 전환이 그림을 바꾸면 안 된다.** 마커 크기 단위가 `scatter`의
  `s`(면적)와 `plot`의 `markersize`(지름)로 다르므로 환산이 필요하다
  (`markersize = sqrt(s)`). 화면·PPT가 같아야 하므로 단계 4에서 캡처 비교로
  확인한다.
- **`plan_workers`가 메모리를 잘못 읽으면** 추출이 느려지기만 하고 실패하지는
  않는다(하한 1). 안전한 실패 방향이다.
